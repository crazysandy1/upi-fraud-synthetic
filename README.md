# UPI Shield: Explainable, Cost-Aware Fraud Detection on Synthetic UPI Transactions

An end-to-end data science project in one Jupyter notebook: [upi_fraud_detection.ipynb](upi_fraud_detection.ipynb).

It flags risky UPI payments, explains every flag in plain English, and chooses the alert threshold by **rupees saved** instead of accuracy.

## How to run

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
.\.venv\Scripts\jupyter notebook upi_fraud_detection.ipynb
``` 

The notebook generates its own data (about 52k payments, 2,000 users, 6 months) and saves it to `data/upi_transactions.csv`. It runs in under a minute on a laptop. No download or Kaggle account is needed.

## Results (June test month)

| Metric | Value |
|---|---|
| PR-AUC: Logistic Regression / Random Forest / XGBoost | 0.85 / 0.94 / 0.95 |
| Recall at the cost-optimal threshold | about 99% |
| Fraud value stopped | about 99.9% |
| Legit payments asked for an extra OTP | about 1.6% |

The scores are high because synthetic patterns are cleaner than real ones. On real bank data, expect lower numbers. The method is what carries over.

## Interview talking points

**30-second pitch.** "I built a UPI fraud model on synthetic data that I generated from four real scam patterns. Instead of raw columns, I built behaviour features that ask 'is this normal for this user?'. I split by time, so I train on the past and test on the future. I compared Logistic Regression, Random Forest and XGBoost using PR-AUC. I picked the threshold that minimises rupee loss, mapped scores to Allow / OTP / Block, and used SHAP to give a plain-English reason for every flag."

**Likely questions and short answers**

- **Why synthetic data?** Real UPI data is private. Public Kaggle UPI files have no user history, so behaviour features are impossible. Synthetic data also tells me the scam type of every fraud row, so I can measure recall per scam type.
- **Why not accuracy?** Only about 2% of payments are fraud. A model that says "never fraud" scores 98% accuracy and catches nothing.
- **Why PR-AUC and not ROC-AUC?** With heavy imbalance, ROC-AUC stays near 1.0 for every model. PR-AUC focuses on the rare class and separates the models clearly.
- **Why a time-based split?** A random split lets the model learn from future payments. That leaks information and inflates scores. A bank always scores tomorrow's payments using yesterday's data.
- **What is data leakage in your features?** Using information that would not exist at payment time. Every feature uses only past payments, for example `shift(1)` before averaging the user's amounts.
- **Why class weights instead of SMOTE?** Class weights make a missed fraud cost more during training. SMOTE creates artificial fraud rows. Weights reach the same goal more simply, without fake data.
- **Why XGBoost?** Fraud depends on combinations of signals (new device + night + high amount). Tree models capture combinations naturally, and XGBoost is the strongest of the three here.
- **How did you choose the threshold?** On the validation month, I computed total cost = missed fraud amount + ₹50 per false alarm for every threshold, and picked the cheapest one. The test month was used only once, for the final score.
- **What does SHAP do?** It splits each risk score into a contribution from each feature. The contributions add up to the score. I turn the top positive contributions into reason codes such as "new device" or "8x the user's usual amount".
- **What are the limitations?** The data is synthetic. The ₹50 friction cost is an assumption. I assume an OTP stops the fraud, but social-engineering victims sometimes share it. There are no graph features for mule rings.
- **What would you do next?** Serve the model behind a FastAPI endpoint, add graph features (shared devices and payees), monitor drift, and retrain with customer fraud reports.
